## Protocolo común

- Antes de tocar un archivo, revisar sus cambios previos. Implementar una tarea y parar tras verificar/marcar.
- **L:** lógica: test significativo primero, `node --test tests/design-system/*.test.mjs` rojo → implementación → verde, `npm run build` y navegador si tiene integración.
- **UI:** registrar primero caso fallido/medición de referencia; no simular render con tests de strings. Por tarea ejecutar `node --test tests/design-system/*.test.mjs` y `npm run build`; fallo de Node detiene la secuencia y no permite comenzar otra tarea. Build fallido también bloquea la tarea. Comprobar el flujo afectado en browser y registrar evidencia. Toda comprobación faltante queda bloqueada, no completa.
- **D:** documentación: integridad/enlaces y datos ficticios; runner si hay contratos de datos. No inventar tests para cambios documentales triviales.
- **V:** verificación: medir y registrar ejecución real; runner y build como base, sin repetirlos por cada captura si no cambió código. El «hecho cuando» de cada tarea se añade a este protocolo.
- Prioridad aprobada explícitamente («si»): ejecutar T51→T52→T53→T54→T55 antes de reanudar T27; luego T27→T28–T50 en el orden original. T51 depende de T14, T52–T54 de T51, T55 de T52–T54; T14 y T26 están completadas, por lo que las correctivas pueden preceder T27 (dependiente de T26). Ejecutar una tarea cada vez y parar.
- Para T51–T55 se requieren capturas/inspección real de navegador de ambos temas y los cuatro diálogos. Las capturas del defecto no prueban corrección. No abrir puertos ni configurar portproxy para llegar a CDP; si no hay navegador accesible, dejar incompleta con bloqueo concreto y pedir evidencia accesible. No marcar solo por test/build.
